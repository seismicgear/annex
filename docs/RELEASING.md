# Cutting an Annex release

This is the operator runbook. `docs/refactor/release-gates.md` lists the gates;
this says what to do with them, in order, and names the two things only a human
can do.

## Published baseline

v0.1.0 and the macOS packaging correction v0.1.1 were published on October 15,
2026. Both tags and their original installers must remain immutable. This runbook is for a future release; it is not a request to
rebuild v0.1.0. See [release evidence](RELEASE_READINESS.md) for completed runs,
Linux v0.1.0 and Mac v0.1.1 native sessions, and the remaining Windows/Linux v0.1.1,
OS-trust, updater, and provider qualification. Repository documentation/license
changes do not alter binary bytes.

## 0. What a release is signed by, and what it is not

Previously published standalone Windows installers have no Authenticode signing. The published v0.1.0 macOS
apps have incomplete bundle signatures. The published v0.1.1 correction uses
ad-hoc signing and strict bundle/native-file verification, without Developer ID
or notarization. See [installation](installation.md) for the current packages. Neither updater signatures nor a successful build establishes
normal browser-download/Gatekeeper acceptance. Do not advise disabling OS
protection to work around a defective package.

What a release IS verifiable by:

* **`SHA256SUMS`**, attached to every release and generated by the workflow
  from the artifacts it just built. This is the verification path to point a
  user at.
* **Tauri updater signatures** (`.sig` files), which sign the updater bundles
  with a key you hold, independent of any certificate authority. Required on a
  tagged release: see §1.
* **The ZK ceremony transcript and per-circuit manifests**, attached to the
  release, so anyone can check what the bundled proving and verification keys
  descend from without cloning the repository.

The standalone tag workflow configures updater signing and local macOS ad-hoc integrity signing. Windows Authenticode
and Apple Developer ID/notarization are not configured. Introducing either
requires its actual credentials, explicit workflow integration, and platform
verification; updater signatures do not establish OS trust.

## Array-managed installations

An installation delivered by Array has one update manager. Array passes the
following nonsecret hints to the installer process and subsequent managed
launches; passing them to the installer also covers its run-after-finish launch:

| Variable | Value |
| --- | --- |
| `KI_ARRAY_MANAGED_INSTALL` | `1` |
| `KI_ARRAY_PRODUCT_ID` | `annex` |
| `KI_ARRAY_BUILD_ID` | The installed build ID |
| `KI_ARRAY_RELEASE_CHANNEL` | `employee`, `beta`, or `stable` |

Annex saves this ownership in `array-managed-installation.json` under its existing
regular data directory. A direct shortcut launch therefore retains Array as its
update manager. An ordinary located/unmanaged installation does not acquire
ownership automatically. Isolated profiles neither save these hints nor update
the installed application. Invalid or unreadable ownership metadata disables the
standalone updater until a valid Array launch restores it; it never falls back
to a public feed.

For a managed installation, Annex does not register the Tauri updater plugin and
its native check/download/install commands refuse the standalone feed. The
Updates dialog opens the fixed `ki-array://updates/annex` link. Array brings its
own interface forward and resolves the current account's release eligibility;
the link does not contain a channel, credential, download URL, or install command.
The displayed last Array channel is a launch observation, not an authorization.
Company access, customer licenses, and product-specific beta admission remain
with their existing authorities.

Standalone Annex installations retain the signed Tauri updater described below.
Array-managed installations still need approved platform publisher verification
and a signed Array manifest for their final artifacts. Tauri signatures,
AuthentiCode/Developer ID signatures, and Array release signatures are distinct
evidence and must not be substituted for one another. Neither updater ownership
nor this handoff changes Annex's identity, stored server data, or license terms.

The focused ownership regressions exercise persisted direct launches, invalid
markers, symlink refusal, isolated profiles and unchanged identity data:

```sh
cargo test --locked --manifest-path scripts/array-update-regressions/Cargo.toml
cd client
npm test -- src/components/DesktopUpdates.test.tsx
```

Native acceptance must still install through Array, exercise Annex, close the
actual process/server before replacement, update to a second release, and verify
the same identity/data and the fixed Array handoff. A webview component test does
not establish that the OS protocol registration or a native installer succeeded.

### Allocated native builds through Array

`.github/workflows/release-array-employee.yml` runs on the existing
`[self-hosted, Windows, X64, array-release]` host and `array-release`
environment. It accepts only this repository's reviewed `main`. Enable automatic
employee publication with `ANNEX_AUTOMATIC_EMPLOYEE_RELEASES=true`; manual
dispatch uses the same checks. Its job-scoped Git configuration keeps canonical
LF source bytes without changing the host's global configuration. It does not
provision a host, paid service, certificate account or artifact-storage tier.

Pin `KI_ARRAY_RELEASE_TOOLS_REF` and `KI_RELEASE_OPERATOR_REF` to full reviewed
commits of the Array publisher and website Store operator. The existing protected
environment provides the approved release key, private Supabase bucket/actor
and Microsoft Artifact Signing configuration. Public policy must explicitly
authorize Annex and its channel keys, with `productPublishers.annex` pinning its
platform publisher. Array's own publisher is not an implicit Annex pin. Cross-
repository checkout credentials are not persisted or passed to the builds.

`scripts/managed-array-release.mjs` supplies the shared publisher's product
callbacks. It first checks the existing source versions, ZK gates, native
ownership regressions, client tests and Rust workspace tests. The publisher
allocates the numeric `x.y.z` version and immutable build ID. Packaging then
clones that exact clean commit into its own disposable directory.

`scripts/managed-array-source.mjs` changes only that isolated copy's native
version: the workspace Cargo version, this workspace's own path dependency
pins/Cargo lock package versions, client/root npm lock version, and Tauri
application version. Third-party package versions, sources, checksums and
dependency constraints stay intact. The original source commit and dependency
lock hashes, transformed lock/file hashes, source version, allocated version and
explicit changed-file receipt are retained. The original checkout is never
rewritten or marked as a fabricated release commit.

The isolated production build verifies the real ZK artifacts and ceremony,
prepares/validates the pinned native resources, and runs Cargo with `--locked`.
Its managed Tauri override emits one NSIS installer, with updater artifacts
disabled and no standalone updater configuration. Source/Rust/frontend stages
run without signing or Store credentials. The later fixed Tauri bundle step
uses the approved native signing command after Tauri's executable patching.
The final application and installer are verified independently by signtool and
Windows Authenticode and matched to Annex's publisher policy. The actual native
file version must match the allocation.

`release-artifacts.json` binds those bytes to their version, build ID, source,
source/packaged dependency locks, policy hash and signer evidence. Array's shared
publisher then uploads the private artifact, signs its employee release
envelope and registers availability. Beta/stable promotions reuse the registered
artifact. No new GitHub public release or `latest.json` is produced by this
managed path. `com.annex.desktop`, `annex-desktop.exe`, the native `annex` protocol,
VRP identity and existing server/user data remain the same application.

The existing Windows x64 host must already have Node 24, Git/Bash, pinned Rust,
MSVC/CMake, Python as required by native tooling, libclang, and the configured
x64 Artifact Signing dlib/signtool/account. The workflow locates the installed
libclang before invoking the publisher; direct operator invocation must provide
its verified `LIBCLANG_PATH`. It installs npm dependencies from the committed
client, ZK and Tauri CLI locks. Production ZK/ceremony gates remain mandatory;
development fixtures cannot stand in for them.

Run the source/version regressions without a native build:

```sh
node --test scripts/tests/managed-array-release.test.mjs
```

The native receipt explicitly records `nativeInstallAcceptance: "not-run"`.
A real fresh install and subsequent Array upgrade still need the Windows
identity/data continuity, process closure and OS protocol/signature acceptance
described above. The workflow retains local build/publication evidence and a
bounded identity/hash summary, cleans its private key inputs, and publishes
installers only through the existing Supabase registry. The historical tag
workflow and its published artifacts remain independent and immutable.

## 1. The updater signing key (one-time, and only you can do it)

Before a desktop build, prepare its native resources on the matching native
runner with `node scripts/prepare-desktop-assets.mjs`, then verify with the same
command plus `--verify`. The release workflow does both on Windows x64, Linux
x64, macOS Apple Silicon, and macOS Intel. All four are required before the
release draft is assembled. The production build hook requires
that verified inventory; it does not accept merely existing speech binaries.
For clean-stage validation without touching an existing checkout's resources,
use `--assets-dir /absolute/staging/assets --work-dir /absolute/staging/build`.
On Windows, use `scripts/prepare-desktop-assets.ps1 -AssetsDir ... -WorkDir ...`;
it selects the installed Visual C++ x64 environment and Ninja before running
the same preparation. Windows Whisper links its C runtime statically.
Windows setup embeds Microsoft's Evergreen WebView2 standalone installer.
Both NSIS and MSI check actual runtime availability through the Microsoft SDK,
repair a missing runtime or stale registration, and check availability again
before reporting success. The shared x86 probe uses the hash-pinned Microsoft
WebView2 SDK 1.0.3800.47 with a static C runtime; its source, SDK archive and DLL
hashes are recorded in the bundled provenance, with the SDK license preserved.
NSIS verifies Microsoft's Authenticode signature before embedding the runtime
installer. The post-bundle gate verifies the actual MSI embedded runtime and
probe bytes, including agreement with NSIS's authenticated runtime input.
The Evergreen installer comes from Microsoft's official current release URL;
its exact executable hash, version and Microsoft signer are recorded per build.
Windows then services that shared Evergreen runtime independently. Annex's
uninstaller does not remove it. This Microsoft signature authenticates the
prerequisite; Annex's own installers still have only updater signatures.
An existing different runtime is refused; preserve it separately before using
an empty destination. `--data-only` prepares verified models and Piper but
deliberately does not produce a complete receipt or permit packaging.

`scripts/desktop-assets.json` pins the official Piper 2023.11.14-2 archives
for Windows x64 and Linux x64, both voice files, the base.en Whisper model and
the semantic embedding files.
Model pins match the immutable revisions and hashes already used in the
Docker/model preparation paths. Piper Linux x64 retains the existing Docker
digest. The Windows archive digest was measured from the named official release
asset over HTTPS on 2026-10-13; the old release API publishes no digest/signature,
so this is a reviewed local pin, not a publisher signature. Recheck the official
source when deliberately updating any pin; do not substitute `latest` or
`resolve/main`.

macOS builds Piper from immutable Piper, piper-phonemize, eSpeak NG, fmt, spdlog
and Sonic source archives on separate native Apple Silicon and Intel runners.
The manifest pins each source commit, archive SHA-256 and byte count, plus the
matching official ONNX Runtime 1.14.1 archive. The old upstream Mac Piper
archives are not packaging inputs: they omit required dylibs, and their ARM
archive contains Intel executables. `scripts/build-macos-piper.mjs` supplies all
dependency locations explicitly and disables unpinned FetchContent downloads.
It bundles the required dylibs, rewrites their non-system dependencies to
`@loader_path`, and refuses wrong-architecture Mach-O files or unresolved
dependencies. Only Apple system libraries may remain outside the bundle.

After changing Mach-O load commands, preparation applies and verifies local
ad-hoc signatures so the native files can execute, including on Apple Silicon.
These signatures do not establish an Apple Developer ID or notarization and do
not provide publisher trust. Preparation then executes the bundled Piper CLI
and synthesizes a nonempty WAV with the pinned voice model. A failed native
launch or synthesis fails resource preparation. Each Mac Piper bundle includes
its component licenses and source/runtime smoke provenance. The corrected
preparation path also signs and verifies Whisper before recording its digest.
After Tauri bundles the app, `scripts/verify-macos-bundle.py` verifies the resource
envelope and every native Mach-O file before upload. It rejects missing seals,
unsigned native code, unexpected bundle identity, and escaping symlinks.

Whisper is compiled from the same immutable v1.7.4 commit pinned by the
Dockerfile, with a static CPU backend and host-specific instruction tuning,
dynamic backend loading, OpenMP, CUDA, Metal and BLAS disabled. Its real
`whisper-cli` target, license, source/flags/compiler-tool provenance and local
binary digest are bundled. This avoids shipping a deprecated `main` stub or
unbundled runtime DLLs. The preparation smoke invokes each real CLI; it is not
transcription or installed-application acceptance. CMake, a native C++ compiler,
Git and tar are required. The macOS Intel and ARM jobs run on matching native
runner architectures. Linux ARM and Windows ARM have no qualified preparation
path and are refused explicitly.

The pinned speech DSP binding also needs libclang at Rust build time. Linux
build stages install `libclang-dev`; Windows and macOS use the runner's LLVM
or Xcode library. `node scripts/verify-libclang.mjs` verifies the directory
and sets `LIBCLANG_PATH` in GitHub Actions. No libclang runtime is bundled
with Annex. CI desktop bundle jobs prepare the same verified speech resources
instead of creating an apparently complete package with empty asset folders.

The complete `assets/desktop-provenance.json` records every resource digest and
the pin-manifest digest. Its generated runtime hashes describe the actual local
compiler output; they are not a claim of bit-for-bit reproducible native builds.
Linux packages use a desktop entry that passes one URL to Annex. The Debian
package requires `desktop-file-utils`; its normal package-manager trigger
refreshes the desktop MIME cache at installation and removal without changing
the user's preferred applications. Install the DEB through `apt install ./Annex_*.deb`
so its declared dependencies are resolved. The build gates inspect both actual
DEB and AppImage desktop entries; the installed desktop audit also requires
cold protocol discovery from a fresh profile before launching Annex.
For the portable AppImage, make it executable and open it once from its permanent
location before opening an invitation. That normal first launch registers its
path with the desktop; moving it requires opening it again. Both registration
utilities and the added utility's license notice are bundled and exercised by
the package gate. Registration errors are shown in the app without preventing
ordinary server connections. Isolated test profiles never change associations.

Installed captions, voice, deep links, updates and uninstall still require
their separate real-session acceptance.

The workflow requires `TAURI_SIGNING_PRIVATE_KEY` and
`TAURI_SIGNING_PUBLIC_KEY` in preflight for both signed drafts and tags.
The release assembly then cryptographically verifies every native updater
artifact and its trusted comment against that public key. A signature file's
presence alone cannot pass this check.

```bash
cargo install tauri-cli@2.11.2 --locked     # if you do not have it
cargo tauri signer generate -w ~/.annex/annex-updater.key
```

That writes two things:

* `~/.annex/annex-updater.key` — the **private** half. Put its contents in the
  repository secret `TAURI_SIGNING_PRIVATE_KEY`, and the passphrase you chose
  in `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Then back the file up somewhere you
  will still have it in three years: losing it means no existing install can
  ever be updated by a key you control, and there is no recovery.
* `~/.annex/annex-updater.key.pub` — the **public** half. It is not a secret.

The public half goes in the repository secret `TAURI_SIGNING_PUBLIC_KEY`.

**Not in `tauri.conf.json`.** The workflow injects it at build time with
`cargo tauri build --config`, and that is deliberate: a key committed to the
tree is either a placeholder — which makes the config look configured while
producing updates nobody can verify — or a real key whose private half somebody
else holds. Keeping it out means the committed config stays truthful about what
it can prove.

Three secrets in total:

| Secret | Half | What breaks without it |
|---|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | private | Tauri produces no `.sig` files |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | private | the signer cannot open the key |
| `TAURI_SIGNING_PUBLIC_KEY` | public | no updater bundles are built at all, and the installed app has no key to verify against |

`tauri-plugin-updater` IS wired into the app now — the dependency, the
`.plugin(...)` registration and the `updater:default` capability. It used to be
listed here as something to do yourself, which meant `createUpdaterArtifacts`
would have produced signed bundles that nothing in the app could consume.

### What the workflow enforces

* Every updater artifact carries its own valid `.sig`; a wrong key, changed
  payload or altered signed comment refuses draft assembly.
* A dry run enforces the same thing a tag does. It previously warned where a
  tag errored, so a green dry run established nothing about the tagged-release
  contract — the only thing a dry run is for.
* `unsigned_dry_run: true` on a `workflow_dispatch` is the single explicit way
  to build without keys. It is refused on a tag.
* `latest.json` is generated from verified signatures and the same canonical
  filenames uploaded to the release. `downloads.json` identifies the exact
  source commit, platform assets, byte lengths and SHA-256 hashes.
* `SHA256SUMS` is produced last and includes both metadata files and all other
  released assets. Duplicate/missing platform outputs refuse assembly.

OS code signing (Authenticode, Apple Developer ID) is a separate decision and
is NOT what any of the above is about. Those integrations remain unconfigured; this
project distributes OS-unsigned installers, verified by `SHA256SUMS` and, for
updates, by the Tauri key above.

## 2. Before you tag

Every gate green on the branch. The ones a release specifically rests on:

```bash
bash scripts/test-all.sh
ANNEX_BUILD_PROFILE=production node zk/scripts/verify-artifacts.js --all
node zk/scripts/verify-ceremony.js
sh scripts/verify-production-rejects-dev-fixtures.sh
bash scripts/tests/version-sync.test.sh
bash scripts/ui-audit.sh        # twice: a recording run proves nothing
bash scripts/desktop-audit.sh
```

Then read the CI run. A green local run is evidence; the CI run is the gate,
and a red check on this repository is a real failure — `RELEASE_READINESS.md`
used to say otherwise and that paragraph is gone.

## 3. Prove the pipeline without tagging

Actions → **Release Desktop App** → Run workflow → `dry_run: true`.

It runs the pre-flight gates, builds the full bundles on Linux, Windows and
both macOS architectures
under `ANNEX_BUILD_PROFILE=production`, builds and **boots** the server tarball,
verifies the pinned ZK artifacts and the ceremony chain, generates `SHA256SUMS`
and the SBOMs, and creates a **draft** release named `dry-run-<sha>`.

What to look at in the run, because each of these was silently absent at some
point:

* **`preflight` ran and passed.** It ties the tag to the version and refuses a
  dev-fixture proving key, before 30-60 minutes of Tauri builds rather than
  after. Both checks run again in `release`, because a `workflow_dispatch` dry
  run reaches that job and a gate a path can skip is not a gate.
* **The updater payloads are in the asset list**, not just their `.sig` files.
  With Tauri 2 `createUpdaterArtifacts: true`, these are native `.AppImage`
  and `.exe` files, and macOS `.app.tar.gz`. Optional MSI files carry their own
  signature. The old `.AppImage.tar.gz`/`.nsis.zip` patterns describe Tauri's
  compatibility mode and do not match this configuration.
* **`SHA256SUMS` covers those bundles and `latest.json`.** A user could
  previously checksum the installer they clicked and not the payload their
  machine fetches unattended — which is the one they never see.
* **The server tarball's `--check` step passed.** That is not a formality: under
  the default posture the server refuses to start without
  `zk/keys/membership_v2_vkey.json`, and under a production profile without
  `assets/embedding/`. Both directories are gitignored and filled by separate
  scripts, so a tarball can look complete and be unbootable.
* **`artifacts/sbom/rust-workspace.json` lists more than one crate's
  dependencies.** `cargo cyclonedx --all` writes one `bom.json` per crate, and
  the old step copied each in turn to the same filename — so "rust-workspace"
  was whichever of the twelve `find` reached last.

Do this before every real tag. A tag is the one action you cannot take back,
and it used to be the only way to find out whether the release job worked.

Delete the dry-run draft afterwards.

## 4. Tag

```bash
# The version in Cargo.toml, tauri.conf.json and client/package.json must
# already agree and already have a CHANGELOG section — scripts/tests/version-sync.test.sh
# checks both.
git tag -a v0.1.0 -m "Annex v0.1.0"
git push origin v0.1.0
```

The `release` job assembles a **draft** GitHub Release. Its body is the
`## [x.y.z]` section of `CHANGELOG.md` — extracted by
`scripts/changelog-section.py`, which fails the release if there is no section —
with GitHub's generated commit list appended. Review it, attach anything
missing, then publish.

Assets: the desktop installers, the updater bundles and their signatures,
`latest.json`, `downloads.json`, `SHA256SUMS`, the SBOMs, and
`annex-server-<version>-x86_64-unknown-linux-gnu.tar.gz`.

The public website uses these stable, architecture-specific installer names:

| Platform | Release asset |
|---|---|
| Windows x64 | `annex-desktop-windows-x86_64.exe` |
| Linux x64 | `annex-desktop-linux-x86_64.AppImage` |
| macOS Apple Silicon | `annex-desktop-macos-aarch64.dmg` |
| macOS Intel | `annex-desktop-macos-x86_64.dmg` |

`scripts/stage-desktop-release.mjs` copies the verified native build outputs to
those names without changing their contents. The macOS updater archives use
the corresponding `.app.tar.gz` names. Publish the verified release before
deploying website links; then check all four real download responses and
correlate downloaded bytes with `downloads.json` and `SHA256SUMS`.

### The container image

`build-image` builds the server image from `Dockerfile` on every run of this
workflow and **pushes only on a tag**, to `ghcr.io/seismicgear/annex:<version>`.
A `workflow_dispatch` therefore proves the Dockerfile still builds and that the
image starts, and publishes nothing — a dry run that pushes is not a dry run.

The job builds with `load: true` rather than `push: true` even on a tag, because
it runs `annex-server --check` inside the image before pushing: the same
question the tarball answers, which is whether the thing STARTS. An image that
built but lost a v2 vkey or the pinned alignment model passes every other gate
here and fails on an operator's machine.

`latest` is deliberately never pushed. The release this workflow assembles is a
DRAFT until a human publishes it, and moving `latest` would hand every
`docker pull` a version nobody had decided to ship. Move it by hand after
publishing:

```bash
docker pull  ghcr.io/seismicgear/annex:0.1.0
docker tag   ghcr.io/seismicgear/annex:0.1.0 ghcr.io/seismicgear/annex:latest
docker push  ghcr.io/seismicgear/annex:latest
```

The release job pushed the image, but anonymous GHCR access returned 403 during
the public-readiness pass. Resolve package visibility before advertising public
`docker pull`. Authorized operators can set `ANNEX_IMAGE`; without it
`docker-compose.prod.yml` builds locally exactly as before:

```bash
ANNEX_IMAGE=ghcr.io/seismicgear/annex:0.1.0 \
  docker compose -f docker-compose.prod.yml pull
```

**Not verified from the development container**: it has the docker CLI but no
daemon, so the image build, the start check and the push have never been
executed — only the workflow's YAML, the compose override in both directions
and the `--check` flag itself were. The first tag, or the first dispatch that
gets a runner, is where this job is proven.

## 5. After

Smoke-test each artifact on a clean machine: install, launch, create an
identity, send a message, uninstall. `scripts/desktop-audit.sh` does the Linux
half in CI; Windows and macOS are hand work, and the point is the paths CI
cannot reach — a `.deb` that installs but leaves no binary on PATH, a
`.desktop` entry that drops the `annex://` scheme handler so every invite link
goes nowhere.

Open `[Unreleased]` in `CHANGELOG.md` for the next cycle.

# Annex Production Invariants

These are the invariants any change — automated or human — must preserve.
Pin this file when assigning a refactor task. If a task requires breaking one
of these, escalate; do not "make tests pass" by relaxing the invariant.

Each invariant has a name, the property, the enforcing code locations, and
the failure modes that must keep being prevented.

---

## I-ZK-1 — ZK enforcement cannot silently degrade

**Property.** When `Config::security::enforce_zk_proofs == true`, every code
path that authenticates a participant must require a real Groth16 membership
proof. The default of `enforce_zk_proofs` is `true`
(`crates/annex-server/src/config.rs::default_enforce_zk_proofs`). A code change
that makes the default `false`, makes the field optional without a default, or
adds a code path that skips proof verification when the flag is true is
forbidden.

**Enforced by:**
- `crates/annex-server/src/config.rs` — field declaration and default.
- `crates/annex-server/src/middleware.rs::verify_zk_proof_payload` (and call sites guarded by `state.enforce_zk_proofs`).
- `crates/annex-server/src/api_ws.rs` — raw-pseudonym auth gate at line ~710 (search `enforce_zk_proofs`).
- Test: `config::tests::default_security_settings` (asserts `enforce_zk_proofs` defaults to `true`).

**Failure mode forbidden:** "Tests fail because of ZK; let me flip the flag in
the test fixture" — the right answer is to provide a real proof (or, for a
test, a fixture with a properly built vkey/proof pair).

## I-ZK-2 — Dummy verification keys are dev-only

**Property.** `annex_identity::zk::generate_dummy_vkey()` is a development
fallback used by `crates/annex-server/src/lib.rs` (search `generate_dummy_vkey`)
when `zk/keys/membership_vkey.json` is missing. Any production build —
desktop bundle, server tarball, container image — must ship a real vkey
generated by `zk/scripts/setup-groth16.js`. Bundles MUST NOT be produced
against a dummy vkey.

**Enforced by:**
- Bundler: `crates/annex-desktop/tauri.conf.json::bundle.resources` lists `../../zk/keys/membership_vkey.json` — this is the file that is shipped and used at runtime.
- Server boot log: when the dummy fallback fires, `crates/annex-server/src/lib.rs` emits a `tracing::warn!` with the explicit instruction to run `node scripts/setup-groth16.js`. CI/release jobs treat that warning as a build smell.
- Release gate: a release artifact must be produced from a tree where `zk/keys/membership_vkey.json` is present and was produced by the trusted-setup ceremony, not synthesized.

**Failure mode forbidden:** Calling `generate_dummy_vkey()` directly from any
non-test code path. It exists only to make local dev usable when keys haven't
been generated yet.

## I-ZK-3 — Membership proofs must bind to the expected identity/session

**Property.** A membership proof's public signals are the **two** values
`[root, commitment]` (in that order), produced by
`zk/circuits/membership.circom::Membership(20)` (`signal output root; signal output commitment;`).
Verification must:
1. Parse the public signals as exactly two field elements in the documented order.
2. Compare `root` against the server's current Merkle root (`state.merkle_tree.root_hex()`).
3. Bind the proof to the caller's claimed pseudonym/commitment by verifying that the same `commitment` is the leaf the caller is using to log in (via `nullifierHex` derived from `commitment` + topic, or via a direct pseudonym-to-commitment lookup).

**Enforced by:**
- `crates/annex-server/src/middleware.rs` — search `// Parse public inputs: [merkle_root, commitment]` (currently around line 551). The function rejects when `current_root != payload.root_hex` (around line 573).
- `zk/scripts/test-proofs.js` (16/16 must pass): asserts root match, commitment match, rejects tampered public signals.
- `annex-identity::nullifier::insert_nullifier` enforces single-use binding per topic.

**Failure mode forbidden:** Accepting a proof but then trusting a separate,
client-supplied `commitment` field instead of the one in the verified public
signals. Or: trusting the proof's `root` instead of the server's current root.

## I-MERKLE-1 — Merkle roots must be canonical and epoch-aware

**Property.** The Merkle tree is depth-`merkle_tree_depth` (default 20),
Poseidon over BN254. The canonical encoding of a root is the field element's
big-endian byte representation, lowercase hex, no `0x` prefix, no leading
zero stripping (i.e. a fixed-width 64-char hex string). All comparisons must
treat the root as a fixed-width hex string of that exact form.

The tree is append-only at runtime. On every server boot, the persisted root
is recomputed from `identities` and compared; mismatch panics with
`MerkleRootMismatch` (see `crates/annex-identity/src/merkle.rs` around line
232). Any feature that mutates leaves in place — re-keying, deletion, bulk
re-insertion — must update both the tree state and a recorded epoch counter,
and must reject inbound proofs whose `root` corresponds to a previous epoch
unless the agent has been migrated to the new root explicitly.

The current code does **not** yet implement epoch metadata explicitly; the
"epoch model" target is described in `zk-merkle-production.md`. Until it
lands, the invariant remains: never silently rotate the root in production.

**Enforced by:**
- `crates/annex-identity/src/merkle.rs` — root recomputation and mismatch panic.
- `crates/annex-server/src/middleware.rs` — current-root comparison.
- `crates/annex-identity/src/registry.rs::get_path_for_commitment` — path generation must match the same tree.

**Failure mode forbidden:** Hex normalization differences (uppercase vs lowercase, leading-zero stripping, decimal vs hex). Always compare against `tree.root_hex()` directly.

## I-AUTH-1 — No raw pseudonym auth in enforced mode

**Property.** When `enforce_zk_proofs` is true, the server MUST reject any
WebSocket / HTTP request that presents only a `pseudonym` parameter without a
session token backed by a verified ZK membership proof. The hot path is
`crates/annex-server/src/api_ws.rs` — the rejection lives just after the
`if state.enforce_zk_proofs` block.

**Enforced by:**
- `crates/annex-server/src/api_ws.rs` (search `state.enforce_zk_proofs`, currently around line 710).
- `crates/annex-server/src/middleware.rs::auth_middleware`.
- Integration tests in `crates/annex-server/tests/api_zk_verify.rs` and `tests/ws_*.rs`.

**Failure mode forbidden:** Adding a "trusted client" or "internal" bypass
that accepts pseudonym-only auth at runtime. Tests that need to exercise the
unauthenticated branch must explicitly construct an `AppState` with
`enforce_zk_proofs = false` and label it as such.

## I-WS-1 — WS protocol shapes must not drift

**Property.** WebSocket frames flowing between `crates/annex-server/src/api_ws.rs`
and `client/src/lib/ws.ts` use a stable JSON shape. Adding fields is
allowed; renaming or removing fields, changing the `type` discriminant
values, or reordering required fields is **a protocol break** and requires a
compatibility shim and explicit task scope.

The current frame discriminants include:
- `subscribe`, `unsubscribe`, `resume` (client → server)
- presence, message, internal warning frames (server → client)

When adding a new frame type, both sides must add a parser and the client
must surface an `internal_error` frame for unknown shapes (already enforced
by tests in `client/src/lib/ws.test.ts`).

**Enforced by:**
- `client/src/lib/ws.test.ts` (`emits internal warning frame for malformed JSON payloads`, `… for unknown/malformed frame shapes`).
- Integration tests in `crates/annex-server/tests/ws_*.rs`.

**Failure mode forbidden:** Tightening the client parser to fail closed on an
unexpected frame instead of emitting `internal_error`; this loses the soft
upgrade story the wire format is designed around.

## I-FED-1 — Federation signature verification cannot be bypassed

**Property.** Every federation envelope crossing
`crates/annex-federation/src/signal.rs` is signed with the originating
server's Ed25519 key and verified at the receiver before any state mutation.
There is no "trusted peer" mode that skips signature verification. If a
signature can't be verified, the envelope is dropped and an event is logged.

**Enforced by:**
- `crates/annex-federation/src/signal.rs` (signing + verification).
- `crates/annex-server/src/api_federation.rs` — call sites that route incoming federation traffic.
- Migrations 017–019 (federation_agreements + remote_handshake metadata).

**Failure mode forbidden:** A "skip verification when the peer is in our
allowlist" option, or accepting envelopes without a signature for any reason
short of a documented bootstrap exception that is itself signed.

## I-DB-1 — SQLite migrations are append-only

**Property.** Every schema change is a new numbered file in
`crates/annex-db/src/migrations/`. The current sequence is
`000_init.sql` … `033_server_public_url.sql`. Numbers are dense and never
reused. Edits to a published migration are forbidden — even comment-only
edits — because some installations have already applied that file and would
re-checksum it.

If a migration is wrong in production, the fix is **another migration** that
corrects the schema. If a migration must be reverted, write an inverse
migration.

**Enforced by:**
- File numbering convention (no tooling enforcement yet — humans must hold the line).
- `crates/annex-db/src/migrations.rs::apply_migrations` (runs files in lexicographic order).

**Failure mode forbidden:** "I'll just fix the typo in `010_messages.sql`" —
no. Add `034_*.sql`.

## I-DESKTOP-1 — Windows + Linux desktop are release-critical

**Property.** Both `windows-latest` (NSIS bundle) and `ubuntu-22.04` (DEB +
AppImage) artifacts must build and run end-to-end before a `v*` tag is cut.
Any change that breaks either platform is a release blocker, not "a future
problem". macOS targets exist in `release-desktop.yml` and may be deferred,
but they MUST NOT be deleted from the matrix; deferred is reversible,
deletion is not.

**Enforced by:**
- `.github/workflows/release-desktop.yml` (matrix entries `x86_64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`).
- `crates/annex-desktop/tauri.conf.json::bundle::linux::deb::depends` and `bundle::windows::nsis`.
- `scripts/build-desktop.js` (cross-platform; `setup-piper.sh` vs `setup-piper.ps1`).

**Failure mode forbidden:** Removing the Windows or Linux job from
`release-desktop.yml` to "unblock" a release. The job stays; the underlying
break gets fixed.

---

## I-DESKTOP-2 — macOS is deferred, not deleted

**Property.** macOS matrix entries (`aarch64-apple-darwin`,
`x86_64-apple-darwin`) remain in `.github/workflows/release-desktop.yml` and
`.github/workflows/ci.yml`, even when they are not yet a release-blocking
target. Code paths that check `cfg(target_os = "macos")` or that name macOS
in `tauri.conf.json::bundle::macOS` stay in place. Removing them silently
costs the project the ability to re-enable macOS without a re-derivation.

**Enforced by:**
- `crates/annex-desktop/tauri.conf.json::bundle::macOS::{entitlements,infoPlist,minimumSystemVersion}`.
- `crates/annex-desktop/Entitlements.plist`, `crates/annex-desktop/Info.plist`.
- `.github/workflows/release-desktop.yml` (macos-latest matrix entries; `Build (macOS)` job in `ci.yml`).

**Failure mode forbidden:** "macOS doesn't ship right now, let me delete the
plist + entitlements + matrix entry to clean up." No — keep them; mark as
non-blocking if needed, but keep them.
